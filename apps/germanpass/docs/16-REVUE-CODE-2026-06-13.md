# Revue de code — GermanPass
**Date :** 2026-06-13  
**Portée :** ensemble du code source (phases 0-9, hotfixes QA du 2026-06-11)

## Résumé exécutif

Le projet est dans un état de production solide. L'architecture (Next.js 15 App Router, Prisma/pgvector, NextAuth v5 JWT + revalidation BDD, Redis, worker async) est cohérente et bien documentée. La sécurité de base est correcte : guards RBAC revalidés en BDD (ADR-004), protection path-traversal, magic-bytes upload, anti-bruteforce Redis, rate-limiting. Onze améliorations ont été appliquées directement ; deux problèmes non bloquants restent documentés ci-dessous.

## Corrections appliquées

### 1. `src/lib/anti-copy.ts` — Catch silencieux → logging
**Problème :** l'échec du calcul d'embedding (ex. AI_API_KEY absente) était avalé silencieusement, rendant l'anti-copie partiellement aveugle sans aucune trace.  
**Fix :** `console.warn` dans le catch avec le message d'erreur.

### 2. `src/lib/rate-limit.ts` — EXPIRE conditionnel (NX)
**Problème :** `redis.expire(key, window)` était appelé inconditionnellement au premier INCR ; en cas de race à la frontière de deux fenêtres, la TTL pouvait être réinitialisée.  
**Fix :** `redis.expire(key, windowSec, "NX")` — la TTL n'est définie que si la clé n'en avait pas.

### 3. `src/lib/recommendations.ts` — Requête N+1 → batch
**Problème :** pour chaque type d'erreur distinct (jusqu'à 3), une requête DB séparée était émise (`lesson.findMany` × N).  
**Fix :** une seule requête récupère toutes les leçons candidates (`OR` sur tous les topics), puis le filtrage par type d'erreur est fait côté JS.

### 4. `src/app/api/learn/lessons/[id]/route.ts` — Rétrogradation COMPLETED → IN_PROGRESS
**Problème :** à chaque relecture d'une leçon terminée, le `upsert` écrasait le statut COMPLETED par IN_PROGRESS, perdant l'avancement du candidat.  
**Fix :** remplacement par une logique conditionnelle `findUnique` + `create`/`update` qui preserve COMPLETED.

### 5. `src/worker/index.ts` + `src/lib/account.ts` — Rappels J-3 jamais déclenchés
**Problème :** le template `accessExpiringSoon` existait dans `mail.ts` mais aucun job ne l'appelait jamais.  
**Fix :**  
- Ajout du type `remind_expiring` dans l'union `Job` du worker  
- Ajout du `setInterval` 24 h + exécution au démarrage  
- Nouvelle fonction `sendExpiringReminders()` dans `account.ts` avec déduplication Redis (clé TTL 25 h pour éviter les doublons)

### 6. `src/lib/ai.ts` — Coût STT toujours 0
**Problème :** `logUsage` était appelé avec `inputTokens: 0, outputTokens: 0` pour Whisper, rendant le suivi de budget inutile pour ce type d'appel.  
**Fix :** estimation de la durée audio depuis la taille du buffer (codec webm/opus ≈ 32 kbps) ; la table PRICING utilise désormais `6_000 USD/1M secondes` (~0,006 $/min).

### 7. `src/app/api/admin/generations/route.ts` — Formats non supportés acceptés
**Problème :** le schéma Zod acceptait `MATCHING`, `GAP_FILL` et `ORDERING` comme formats de génération IA, alors que le prompt ne produit pas la structure `metadata` requise pour ces formats (ce qui aurait rendu les questions incorrigibles après validation).  
**Fix :** restreindre `taskFormat` à `["MCQ_SINGLE", "MCQ_MULTI", "TRUE_FALSE"]` avec un commentaire expliquant pourquoi.

### 8. `src/lib/db.ts` — Query logging désactivé en dev
**Problème :** le niveau `["warn", "error"]` ne loggait pas les requêtes SQL en développement, rendant le débogage des N+1 difficile.  
**Fix :** niveau `["query", "warn", "error"]` en `development`, `["warn", "error"]` en production.

### 9. `src/lib/env.ts` — Avertissements de configuration manquants
**Problème :** une `AI_API_KEY` absente en production ne provoquait une erreur qu'au premier appel IA réel, sans warning au démarrage.  
**Fix :** deux `console.warn` non bloquants au chargement du module : un pour `AI_API_KEY` absent en production, un pour `GOOGLE_CLIENT_ID`/`SECRET` définis de façon asymétrique.

### 10 & 11. `src/lib/progress.ts` — Division par zéro défensive
**Problème :** les calculs `v.ok / v.total` pouvaient théoriquement produire `NaN` si `total` était 0 (le filtre `take: 500` ne garantit pas la présence de données).  
**Fix :** guards `v.total > 0 ? ... : 0` sur les deux calculs de pourcentage.

## Problèmes non corrigés (recommandations)

### A. Ingestion RAG — pas de limite de concurrence
Dans `worker/jobs/ingest.ts`, les embeddings sont traités par batches de 64 mais il n'y a pas de limite de concurrence si plusieurs jobs d'ingestion arrivent simultanément (gros fichiers). Recommandation : ajouter un sémaphore Redis ou une queue dédiée si la bibliothèque RAG dépasse ~50 documents.

### B. JWT callback — requête DB à chaque refresh
Dans `src/auth.ts`, le callback `jwt` effectue un `db.user.findUnique` à **chaque** rafraîchissement de token (toutes les 7 jours max). C'est intentionnel (ADR-004 : revalidation du rôle) mais déclenche aussi une requête sur la première émission du token, ce qui est redondant puisqu'on vient juste de s'authentifier. Impact : négligeable en production, mais à surveiller si la base est lente.

### C. TestDaF non couvert
Analyse faite (cf. DECISIONS.md et mémoire projet) mais non implémentée. 5e provider avec des verdicts TDN spécifiques. À planifier si la demande est avérée.

### D. Emails en production — pas de retry
`sendMail` est appelé avec `.catch(() => undefined)` partout (comportement voulu pour ne pas bloquer). Si le serveur SMTP est temporairement indisponible, l'e-mail est perdu sans trace. Pour la production, envisager de pousser les e-mails dans la queue Redis avec retry.

## Points forts confirmés

- **Correction déterministe** (`src/lib/correction.ts`) : 6 formats, crédit partiel, 100 % de branches couvertes en tests.
- **Scoring modulaire** (`src/lib/scoring.ts`) : les quatre providers sont correctement modélisés (Goethe modulaire, ECL moyenne+minimum, TELC séparation oral, ÖSD global).
- **Path traversal** (`src/lib/storage.ts`) : `path.resolve` + vérification `startsWith(base + sep)` — correct.
- **Anti-bruteforce** (`src/lib/rate-limit.ts`) : compteur Redis par `email+ip`, verrou configurable.
- **RGPD** : export JSON complet, soft-delete + anonymisation immédiate, consentement audio révocable.
- **Schéma Prisma** : indexes ciblés sur les colonnes de filtre les plus fréquentes (`status`, `userId + createdAt`, `dueAt`).
- **Pipeline génération IA** : RAG → Zod → anti-copie → PENDING_REVIEW est robuste et testable.

## Avant mise en production

1. Exécuter `npm run typecheck && npm run lint && npm test` (les fixes #3 et #4 introduisent des changements comportementaux à vérifier).
2. Vérifier que la migration `Lesson.helpFr/helpEn` est bien passée (cf. mémoire projet).
3. Configurer `PAYMENT_ORANGE_MONEY`, `PAYMENT_MTN_MOMO`, `PAYMENT_PAYPAL` dans `.env`.
4. Alimenter la bibliothèque RAG et assembler ≥ 1 examen blanc par cible (cf. 12-RECETTE.md).
