# Revue de code — GermanPass SaaS — 2026-06-18

## Verdict global

Le projet est d'une **qualité professionnelle élevée** pour un SaaS en solo. Architecture cohérente, sécurité rigoureuse, RGPD soigné. Les 7 corrections appliquées ci-dessous sont des ajustements de robustesse — aucun bug critique n'a été trouvé.

---

## Points forts (à conserver)

### Sécurité
- **Guards systématiques** (`requireAdmin`, `requireStudent`, `requireFullPlan`, `requireAuthenticated`) avec revalidation DB à chaque requête API — invalide les sessions même avec JWT encore valide (ADR-004 respecté).
- **Anti-bruteforce** login + register + forgot-password avec rate-limit fenêtre fixe (Redis INCR/EXPIRE NX atomique).
- **Path traversal** bloqué dans `storage.ts` (`path.resolve` + startsWith check).
- **Détection MIME par magic bytes** — jamais par Content-Type client.
- **`sanitizeQuestion`** : isCorrect, accepted, correctOrder, pairs jamais envoyés avant soumission.
- **CSP** configuré dans `next.config.ts` (HSTS, X-Frame-Options, Permissions-Policy inclus).
- **Token reset mot de passe** : opaque 32 octets / TTL 1 h / usage unique / invalidation inverse.

### Architecture
- Fonctions pures et testables : `scoring.ts`, `correction.ts`, `srs.ts`, `account.computeNewAccessUntil`.
- `guards.ts` centralisé, `audit.ts` systématique sur toutes les actions sensibles.
- Budget IA mensuel par utilisateur, logging de coût/latence pour chaque appel.
- Worker asynchrone séparé (BRPOP) avec cron interne — zéro long-polling dans Next.js.
- PWA offline avec IDB + sync automatique au retour réseau.

### RGPD
- Soft-delete + anonymisation immédiate (`email → deleted-<id>@deleted.invalid`).
- Export JSON téléchargeable de toutes les données personnelles.
- Consentement audio Sprechen traçé (`audioConsentAt`).

## Corrections appliquées

### 1. `src/auth.ts` — DB lookup JWT inutile à chaque refresh de token

**Problème :** Le callback `jwt` appelait `db.user.findUnique` à chaque vérification de session (chaque requête serveur en SSR/RSC). En production avec N utilisateurs actifs, cela multiplie les requêtes DB inutilement.

**Correction :** La requête DB ne se fait plus que lors du login initial (`user` défini), pas sur les refreshs de token suivants. Le rôle est encodé dans le JWT dès la première connexion.

> **Note opérationnelle :** Si le rôle d'un utilisateur est modifié en prod (passage STUDENT → ADMIN), il faut que l'utilisateur se reconnecte pour que son token soit mis à jour. Comportement standard pour les JWT.

### 2. `src/lib/mail.ts` — `process.env.APP_URL` remplacé par `env.APP_URL`

**Problème :** La constante `APP_URL` lisait `process.env.APP_URL` directement au lieu du singleton `env` validé par Zod. Incohérence — une valeur malformée aurait pu passer sans être détectée au démarrage.

**Correction :** Utilisation de `env.APP_URL` (singleton déjà validé à l'import du module).

### 3. `src/lib/ai.ts` — `embed()` ne vérifiait pas le budget IA

**Problème :** `chatCompletion()` appelle `checkBudget()` mais `embed()` ne le faisait pas. Un utilisateur (ou un job admin) aurait pu générer des embeddings en masse sans être coupé par le plafond mensuel.

**Correction :** `checkBudget(userId)` ajouté en tête de `embed()`.

### 4. `src/app/api/files/[...path]/route.ts` — Cache-Control des fichiers sensibles

**Problème :** `Cache-Control: private, max-age=3600` s'appliquait à tous les fichiers, y compris les preuves de paiement (`proofs/*`) et les enregistrements audio Sprechen (`audio/*`). Ces fichiers ne doivent jamais être mis en cache (données personnelles).

**Correction :** `Cache-Control: no-store` pour `category === "proofs"` et `category === "audio"`. Les fichiers TTS et stimuli conservent `private, max-age=3600`.

### 5. `next.config.ts` — `worker-src 'self'` manquant dans le CSP

**Problème :** Le Service Worker Serwist (`/sw.js`) est un worker-scope. Sans `worker-src` explicite, certains navigateurs peuvent refuser d'enregistrer le SW ou déclencher des avertissements CSP.

**Correction :** Ajout de `worker-src 'self'` dans la directive CSP.

### 6. `src/app/api/practice/attempts/route.ts` — Race condition sur le random sampling

**Problème :** Le pattern `count() → skip: random * count` ouvre une race condition : entre les deux requêtes, un passage peut être dépublié, ce qui fait que `findFirst` renvoie `null` même si `count > 0`.

**Correction :** On sélectionne d'abord la liste des IDs (`findMany({ select: { id: true } })`), puis on tire un ID au hasard côté JS, et on fait une requête `findFirst` avec ce seul ID. L'ensemble est cohérent et si le passage disparaît entre les deux requêtes, le NOT_FOUND est retourné proprement.

### 7. `src/lib/account.ts` — `expireOverdueAccounts` séquentiel → optimisé

**Problème :** La boucle `for (const u of overdue) { await db.user.update(...) }` fait N requêtes DB séquentielles. Si 200 comptes expirent la même nuit, le cron met plusieurs secondes à terminer.

**Correction :**
- `db.user.updateMany` pour mettre à jour tous les comptes expirés en une seule requête.
- Audits en `Promise.all` (parallèles).
- Emails en `Promise.allSettled` fire-and-forget (non bloquants, les erreurs SMTP ne font pas planter le cron).

## Points d'attention non corrigés (à traiter selon priorité)

### A. `src/app/api/admin/progression/route.ts` — pas de pagination

La route charge les 100 premiers étudiants sans pagination. À surveiller si la base dépasse quelques centaines d'utilisateurs. Ajouter `page` / `pageSize` comme dans `/api/admin/users`.

### B. `src/lib/rate-limit.ts` — atomicité INCR/EXPIRE

Le code fait `INCR` puis `EXPIRE NX` en deux opérations séparées. Si le process crash entre les deux, la clé Redis reste sans TTL (fuite mémoire). Très peu probable en pratique mais pourrait être sécurisé avec un pipeline MULTI/EXEC ou un script Lua.

### C. Rôle JWT non rafraîchi après modification admin

Si l'admin change le `role` d'un utilisateur (ex. promotion en admin), la session JWT existante de cet utilisateur conserve l'ancien rôle jusqu'à déconnexion/reconnexion. Pour les STUDENT promus ADMIN, ce n'est pas un risque de sécurité (les guards vérifient la DB), mais c'est une expérience UX dégradée. Solution : invalider les sessions côté Redis avec `next-auth` + `SessionAdapter` ou demander à l'utilisateur de se reconnecter.

### D. `src/lib/marketing.ts` — pattern "at-most-once" pour les emails

La suppression du Sorted Set Redis se fait **avant** l'envoi de l'email (pattern at-most-once). En cas de crash du process juste après le `zrem` et avant `sendMail`, l'email n'est jamais envoyé. Acceptable pour des emails marketing mais à documenter explicitement. Si ce comportement pose problème : passer à "at-least-once" (supprimer après succès, avec déduplication par clé Redis).

### E. `next.config.ts` — CSP `unsafe-inline` + `unsafe-eval`

Contrainte Next.js (scripts inline nécessaires pour l'hydration et les RSC). Pas de contournement simple sans migration vers un nonce-based CSP, qui demande un effort non négligeable. À considérer si le contexte de sécurité l'exige.

### F. `src/worker/jobs/ingest.ts` — nouvelle instance PrismaClient par job

Le worker crée `new PrismaClient()` en tête de fichier (instance du module). C'est correct dans ce contexte (process séparé) mais si le worker est un jour intégré dans le process Next.js, il faudra partager l'instance de `db` depuis `src/lib/db.ts`.
